# etl/federal

A Ruby ETL that turns the HTML/CSV editions of the _Public Accounts of
Canada_ into structured JSON, for the federal spending pages under
`/federal/spending` (see `docs/specs/federal-public-accounts-pipeline.md`).

## Provenance

This is a trimmed copy of the `public_accounts` Ruby CLI (`pb`), copied into
this repo on **2026-07-05**. The original repo also builds a 2.3 GB SQLite
database, imports StatCan bulk datasets, and generates Datasette metadata —
none of that came along. Only what this repo's federal spending pipeline
needs was kept:

- The CLI shell (`bin/pb`, `lib/pb_cli.rb`) and five commands: `scrape`,
  `extract`, `download-tables`, `validate`, and `export` (§7 site contracts).
- The three HTML extractors (`major_transfers_by_provinces_and_territories`,
  `transfer_payments_by_ministry`, `budgetary_details_by_allotment`) and
  their shared `Base` class.
- The one existing validator (`major_transfers_by_provinces_and_territories`)
  and its `CommonAssertions`/`Base` support code.
- `table_mapping_parser.rb` and `open_canada_api.rb`, used by
  `download-tables` to resolve Open Government open-data CSV/dataset URLs.
- The already-extracted intermediate JSON (`extracted/data/*.json`, ~17 MB) —
  the canonical output of `pb extract` as of the copy date. These are
  committed because they're the input the (forthcoming) `export` step
  consumes; they are not regenerated by CI.
- The Open Data table mapping CSV (`open_tables/mapping/table_mapping.csv`).
- Three Vol I consolidated-statement CSV editions
  (`open_tables/data/cdeif-tycfi-{2023-eng,2024,2025}.csv`, "Ten Year
  Comparative Financial Information"). `open_tables/data/*.csv` is otherwise
  gitignored; these three are explicitly un-ignored (see `.gitignore`) so the
  headline totals, revenue lines, and the six vol1-sourced thematic nodes are
  reproducible offline. Together they cover fiscal years **2014–2025** (each
  edition is a rolling ten-year window; the 2013 ending year would require the
  2022 edition, which is not available — hence 2013 is excluded from export).
- A CPI reference dump (`reference/cpi_fiscal_year.json`) — see below.

Left behind: `create-db`, `create-views`, `create-metadata`,
`import-tables`, `create-inflation-adjusted-tables`, `statscan`, `gen-bcid`,
`initialize`, the SQLite database itself, and the StatCan bulk-download
machinery. If a future phase needs any of those, pull them from the source
repo (`public_accounts`, currently at `/Volumes/floppy/public_accounts`) the
same way this trim was done.

The French translation and prose-generation pipeline (`harvest-glossary`,
`translate`, `prose`; spec §8–§9) was added on 2026-07-05 -- see "French
translation & department prose" below.

## Setup

```bash
cd etl/federal
bundle config set --local path 'vendor/bundle'   # keep gems out of the system Ruby
bundle install
```

## Running

All commands are run from `etl/federal/` (or via the full path — `bin/pb`
locates its own `Gemfile` regardless of your working directory):

```bash
# 1. Scrape raw HTML/PDF for one or more Public Accounts years (network-heavy,
#    writes to ./raw/<year>/, gitignored)
bin/pb scrape 2013-2025

# 2. Extract structured JSON from the scraped HTML into ./extracted/data/
bin/pb extract                                              # all 3 extractors
bin/pb extract major_transfers_by_provinces_and_territories # just one

# 3. Validate (currently covers major_transfers_by_provinces_and_territories;
#    requires a SQLite db built from the extracted JSON — not part of this
#    trimmed pipeline yet)
bin/pb validate

# 4. Download the Open Government open-data CSV tables (used for Vol I
#    consolidated statements) into ./open_tables/data/ (gitignored)
bin/pb download-tables
```

```bash
# 5. Export the site JSON contracts (spec §7) into /data/federal.
#    Reads extracted/data/*.json (Vol II) + open_tables/data/cdeif-*.csv
#    (Vol I) + mappings/{thematic_tree,ministry_slugs}.yaml + the CPI
#    reference. Default --out is ../../data/federal (the repo's /data/federal).
bin/pb export --year 2024            # single year
bin/pb export --all-years            # all years with data (2014–2025)
bin/pb export --all-years --out DIR  # custom destination
```

`export` is deterministic (fixed field order, floats rounded — billions to 6
places, line-item dollars to integers) so JSON diffs are reviewable. Set
`PB_EXPORT_TIMESTAMP` to pin `generatedAt`/`updatedAt` for reproducible runs.

Validation (spec §5) is enforced during export: every non-total allotment row
must resolve to a slug and a thematic node; every Sankey parent must equal the
sum of its children within $1M; and hard-coded published Vol I headline totals
(2024: $513.94B spending / $459.53B revenue) are asserted within 0.5%. On a
violation the offending year is excluded, the reason is written to
`export_errors.md`, and the remaining years still ship; a true validation
failure (unmapped row, unbalanced node) additionally exits non-zero.

**Per-year output** (`data/federal/{year}/`): `summary.json` (Vol I headline
totals + per-ministry Vol II shares + CPI multiplier), `sankey.json` +
`sankey.full.json` (thematic spending tree over Vol II allotments plus six
Vol I-sourced nodes, and a Vol I revenue tree; truncated top-12+Other vs
untruncated), `reconciliation.json` (Vol I ↔ Vol II bridge), `i18n/fr.json`
(empty placeholder for the translation phase), and `departments/{slug}.json`.
Plus `data/federal/index.json` (available years, default 2025, ministry list,
`departmentsByYear`).

## French translation & department prose (spec §8–§9)

Three more commands, all reading/writing under `data/federal/{year}/`
(produced by `pb export`) and configured entirely by files in this repo --
`mappings/glossary_fr.yaml` and `prompts/*.md`:

```bash
# 1. Harvest official EN->FR term pairs from the bilingual open.canada.ca
#    Public Accounts CSVs into mappings/glossary_fr.yaml. Only needs
#    re-running when a new open-data edition is downloaded; the checked-in
#    result was harvested from the full corpus at
#    /Volumes/floppy/public_accounts/open_tables/data (read-only; only 3 of
#    those ~114 CSVs are committed into this repo's own open_tables/data,
#    per the CPI/Vol I note above).
bin/pb harvest-glossary --source /Volumes/floppy/public_accounts/open_tables/data
bin/pb harvest-glossary                      # uses this repo's open_tables/data instead

# 2. Translate every Sankey node, department name, entity, vote description,
#    transfer-payment description, and reconciliation item name to French.
bin/pb translate --year 2025
bin/pb translate --all-years

# 3. Generate department prose (English only; French prose translation is a
#    follow-up pass through the same translate pipeline, not yet wired in).
bin/pb prose --year 2025                      # every department that year
bin/pb prose --year 2025 --department transport-canada
```

`translate` and `prose` both call the Claude API (`ANTHROPIC_API_KEY` env
var; plain `Net::HTTP` against `POST /v1/messages`, model `claude-opus-4-8` --
no `anthropic` gem dependency) and are no-ops on already-resolved,
unchanged content, so re-running either is safe and cheap.

### Translation pipeline (`bin/pb translate`)

1. **Collect**: every translatable string in `sankey.json`, each
   `departments/{slug}.json` (department display name by slug; mini-Sankey
   node names; entity names; vote descriptions; transfer-payment
   descriptions), and `reconciliation.json` item names -- each keyed by its
   stable `id` (or `slug` for department names), matching exactly how
   `src/lib/federal.ts` looks French strings up at render time.
2. **Glossary pass** (no API call): exact and case-normalized matches
   against `mappings/glossary_fr.yaml` resolve immediately. `Glossary` also
   expands the "Vote N" pattern ("Vote 1", "Vote 10", ...) via the
   glossary's single `Vote` -> `Crédit` term, since the literal vote labels
   are site-synthesized ("Vote " + code) rather than a value that appears
   verbatim in the open-data CSVs. As of the 2025 harvest, roughly **85% of
   all labels across all years** resolve here with zero API cost.
3. **LLM pass**: whatever's left is batched (40 ids per request) to the
   Claude API, with the subset of the glossary relevant to that batch
   injected as required terminology (`prompts/translation.md`), and parsed
   back as a strict `{"id": "french text", ...}` JSON map.
4. **Incremental**: `data/federal/{year}/i18n/fr.hashes.json` stores a
   SHA-256 of each id's English source text. On the next run, an id is
   retranslated only if its source text changed or it's new -- existing
   `fr.json` entries are left untouched. `fr.json` itself stays the flat
   `id -> string` map the site loader requires (no hash metadata inside it).
5. **Write**: both `fr.json` and `fr.hashes.json` are written sorted by key,
   so PR diffs show exactly what changed.

### Prose pipeline (`bin/pb prose`)

For each department-year, builds a prompt from **only that
department-year's** `departments/{slug}.json` (plus `summary.json` for
federal-total framing) instructing the model to write ~3 short, neutral
paragraphs -- see `prompts/prose.md`. All figures must use one of the three
placeholder tokens the site actually interpolates
(`src/app/[lang]/(main)/federal/spending/[year]/[department]/page.tsx`,
`renderProse()`): `{{name}}`, `{{totalSpending}}`, `{{percentageOfFederal}}`.
Any other `{{...}}` token would silently render as an empty string on the
site, so the lint step (below) rejects it as if it were a bad figure.

A second API call (`prompts/prose_verify.md`) fact-checks the draft against
the same JSON and is appended as an HTML comment block at the end of the
file for human review -- it never blocks writing the file, only flags
what to double-check before setting `reviewed: true`.

Output: `data/federal/{year}/departments/{slug}.prose.en.md`, gray-matter
frontmatter `reviewed: false`. The 14 legacy departments' FY2024 pages
(`existing_page: true` in `mappings/ministry_slugs.yaml`) are skipped --
their hand-written prose is preserved separately, not regenerated.

**Lint (`PbCli::Prose::Lint`)**: rejects any draft containing a literal
dollar figure (`$` followed by a digit) or percentage (`\d+%`) outside a
`{{placeholder}}`, or a `{{...}}` token that isn't one of the three
supported ones. A lint failure stops before the (billed) verification call
and before the file is written -- nothing partially-correct is ever
committed to disk.

### Review workflow

`fr.json`, `fr.hashes.json`, and `*.prose.en.md` are all **committed,
PR-reviewed artifacts** -- generated by a pipeline run, not at site build
(same model as `pb export`'s JSON contracts). Concretely:

- French labels ship as soon as `fr.json` is committed -- there's no
  separate "reviewed" gate for translations, since a glossary/LLM-resolved
  label falling back to English (`lang="en"` per spec §8) is a safe failure
  mode either way.
- Prose only renders once a human flips `reviewed: false` -> `true` in the
  file's frontmatter. Until then the department page renders stats-only
  (`getFederalDepartmentProse` returns `reviewed: false`, and the page
  treats that as "don't show prose yet") -- so a data-pipeline re-run can
  regenerate a draft without ever affecting what's live. Use the appended
  verification comment block as your review checklist, then delete it (or
  leave it; it's an HTML comment and never renders) once you flip the flag.

### Cost expectations

Both commands are cheap relative to a full `pb export` re-run, and
incremental by design so a routine re-run after a data update only pays for
what actually changed:

- **Translate, full corpus** (`--all-years`, all 12 years, first run with an
  empty `fr.json`): ~18,900 translatable labels, ~85% glossary-resolved
  (free), leaving ~2,800 for the LLM in ~70 batched requests of 40 items
  each. At typical batch sizes (~1.5-2.5K input tokens, ~500-700 output
  tokens per request, Claude Opus 4.8 pricing) this is on the order of
  **$1-3 total** for every year's labels from scratch. A routine re-run
  after a data refresh only retranslates ids whose English text actually
  changed -- typically a handful of requests, well under $0.10.
- **Prose, full corpus** (every department-year except the 14 legacy
  FY2024 pages): ~296 department-years x 2 calls (draft + verify) = ~590
  requests. At typical context sizes (~1-2.5K input tokens per call including
  the department JSON, ~150-700 output tokens) this comes to roughly
  **$10-15 total** for a first full run. Prose isn't hashed/incremental like
  translation -- re-running `pb prose` for a department-year always
  regenerates and overwrites its draft (the `reviewed` flag is what protects
  already-approved copy from being silently replaced; re-review after
  regenerating).

These are estimates based on prompt/context sizes, not a metered production
run across the full corpus -- treat them as an order-of-magnitude budget,
not an invoice.

## Fiscal year convention

Canada's fiscal year runs April 1 – March 31. Following the source ETL, all
extracted and exported data uses the **ending year** of the fiscal period:

- "2016-2017" (older Public Accounts HTML formatting) → fiscal year **2017**
- "2019-2020" → fiscal year **2020**
- Public Accounts _2024_ = the fiscal year ended 2024-03-31

Site URLs use the ending year (`/federal/spending/2024`); display strings
should render as "FY 2023–24".

## CPI reference (`reference/cpi_fiscal_year.json`)

A compact dump of two small reference tables from the source repo's SQLite
database (`public_accounts.db`: `cpi_inflation_indexes` and
`calendar_cpi_inflation_indexes`), read via `sqlite3` in read-only mode and
copied verbatim on 2026-07-05. Source: Statistics Canada Table 18-10-0004-01
(Consumer Price Index, monthly). See the file's own `_provenance` field for
full detail. This backs the `summary.json.inflation.multiplierToBase` field
described in the spec (§2, "Inflation").

Schema:

```jsonc
{
  "_provenance": { "...": "source, license, and column semantics" },
  "cpi_inflation_indexes": {
    "primary_key": "fiscal_year",
    "rows": [
      {
        "fiscal_year": 2017,
        "avg_cpi": 128.4,
        "months_count": 12,
        "index_2017": 1.0,
        "index_2018": 1.023,
        /* ... */ "index_2025": 1.27,
      },
    ],
  },
  "calendar_cpi_inflation_indexes": {
    "primary_key": "calendar_year",
    "rows": [
      /* same shape, keyed by calendar_year */
    ],
  },
}
```

`index_YYYY` on a given row is the multiplier to convert that row's-year
dollars into YYYY dollars (e.g. the `fiscal_year: 2017` row's `index_2023`
value multiplies FY2017 dollars up to FY2023 dollars).
